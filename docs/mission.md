# 一、项目定位

这是一个面向 **房东、租客、管理员** 三类用户的房屋租赁平台，核心目标是把传统租房流程中的：

- 找房
- 沟通
- 预约看房
- 签约
- 缴租
- 报修
- 投诉
- 管理统计

尽量搬到线上，并加入一定的“智能化”能力，比如智能搜索、推荐、智能问答。

------

# 二、先明确系统边界

为了后面不做乱，先把“本系统负责什么、不负责什么”定清楚。

## 1. 系统负责的内容

系统内应该完成这些主要业务：

- 用户注册、登录、身份区分
- 房源发布、编辑、下架、展示
- 房源搜索与推荐
- 房东和租客在线消息沟通
- 看房预约
- 合同生成/签约记录
- 租金支付记录
- 维修申请
- 投诉处理
- 管理员后台管理与统计报表

## 2. 系统不一定要在第一版做得很深的内容

这些内容可以先做“简化版”：

- 电子合同的法律合规签章
- 真正的第三方支付接口
- 真正的多因素认证
- 智能客服大模型深度接入
- 视频看房超大文件处理
- 高级风控和审计系统

也就是说，课程项目第一版要先把**完整业务闭环**跑通，再考虑做“高级能力”。

------

# 三、用户角色分析

文档里已经明确了三类用户：房东、租客、系统管理员。
 我们把他们的核心职责再细化一下。

## 1. 房东

核心目标：**发布并管理房源，处理租赁事务**

主要操作：

- 发布/编辑/删除房源
- 上传图片、视频
- 设置房源状态
- 接收预约并确认
- 与租客沟通
- 发布新闻/通知
- 查看租金收入
- 处理报修申请
- 处理投诉相关问题

## 2. 租客

核心目标：**找房并完成租住过程**

主要操作：

- 注册、登录、完善资料
- 搜索房源、查看详情
- 收藏/对比房源（建议新增）
- 在线咨询房东
- 预约看房
- 在线签约
- 查看和支付租金
- 提交维修申请
- 发起投诉

## 3. 系统管理员

核心目标：**维持平台正常运行**

主要操作：

- 管理用户
- 审核/管理房源
- 处理投诉
- 查看系统日志
- 查看统计报表
- 维护公告/基础数据

# 四、功能模块划分

你文档中的功能点比较多，建议拆成下面 8 个一级模块。这样最清晰，也最适合后面做菜单和数据库设计。

## 1. 用户与权限模块

包含：

- 注册
- 登录
- 退出登录
- 找回密码
- 个人信息维护
- 身份认证
- 角色权限控制

### 设计建议

这里要做到“**一个用户一个账号，一个账号一种主角色**”。
 不要一开始就做得太复杂，比如一个人同时是租客和房东，这会把权限逻辑搅乱。第一版建议：

- 注册时选择角色
- 角色固定
- 后期如需扩展，再支持多角色切换

------

## 2. 房源管理模块

包含：

- 房源发布
- 房源编辑
- 房源删除
- 房源上下架
- 房源状态维护
- 图片/视频上传
- 房源详情展示

### 房源状态建议统一枚举

建议不要只写“空置、出租中、维修中”，而是设计成：

- 待审核
- 已上架
- 已下架
- 已预约
- 已出租
- 维修中
- 已删除

这样后面流程才不会乱。

------

## 3. 搜索与推荐模块

文档里写了按地区搜索、按户型搜索，并提到智能推荐。

### 基础搜索条件建议包括

- 区域
- 小区/地址关键词
- 户型
- 租金区间
- 面积区间
- 装修情况
- 房源状态

### 推荐功能建议先做简化版

第一版不要做复杂 AI 推荐，做一个“规则推荐”就够：

- 同区域推荐
- 同价位推荐
- 同户型推荐
- 热门房源推荐
- 最新发布推荐

这样既能叫“智能推荐”，又能做得出来。

------

## 4. 消息与内容模块

文档中有“留言管理”和“新闻管理”。

建议拆成两个子模块：

### A. 在线消息模块

- 房东与租客私信沟通
- 会话列表
- 消息记录
- 未读提醒
- 与房源关联的咨询

### B. 新闻/公告模块

- 房东发布租赁相关消息
- 新闻的增删改查
- 管理员发布平台公告（建议新增）

### 智能代理答疑

文档提到“可以通过一个智能代理替房东回答租客一些基本信息”。
 这个建议做成：

- 预设问答模板
- 或基于房源字段自动回答

例如：

- “这个房子多少钱？”
- “几室几厅？”
- “押金多少？”
- “能不能养宠物？”

第一版不用真的接大模型，先做规则式机器人更稳。

------

## 5. 租赁业务模块

这是核心流程模块，文档写得很明确：预约看房、在线签约、租金支付管理。

### A. 看房预约

建议流程：

1. 租客选择房源和时间
2. 提交预约申请
3. 房东确认/拒绝
4. 生成预约记录
5. 预约结果通知双方

### B. 在线签约

建议简化为：

- 由系统根据模板生成合同
- 双方确认信息
- 提交签约记录
- 合同状态变为已签署

第一版可以不做真正电子签章，只做“合同记录 + PDF/页面展示”。

### C. 租金支付

第一版建议：

- 做“支付记录管理”
- 不一定接真实支付平台
- 可支持“模拟支付”

状态可以有：

- 待支付
- 已支付
- 已逾期
- 已取消

------

## 6. 维修与投诉模块

文档里这部分比较典型，也适合做课程项目展示。

### A. 维修申请

建议流程：

1. 租客提交维修申请
2. 选择房源/合同
3. 填写问题描述
4. 房东接单/处理
5. 更新处理状态
6. 租客确认是否解决

状态建议：

- 待处理
- 处理中
- 已完成
- 已关闭

当前第一版补充约束：

- 报修必须基于当前租客自己的 `active contract` 创建
- 第一版不做附件上传，`image_url` 不进入当前公开模型
- 主流程为 `pending -> processing -> completed -> closed`
- 可选分支保留 `rejected / cancelled / reopened`
- tenant 负责 `create / close / reopen`
- landlord 负责 `process / complete / reject`
- admin 复用同一套接口，可执行所有合法状态流

### B. 投诉管理

建议流程：

1. 租客提交投诉
2. 选择合同/房源上下文
3. 房东处理反馈
4. 管理员可按需介入
5. 关闭投诉单

状态建议：

- 待受理
- 处理中
- 已处理
- 已驳回
- 已关闭

当前第一版补充约束：

- 投诉必须基于当前租客自己的 `active contract` 创建
- 第一版不做附件上传，不做 `target_type / target_id` 这类泛化投诉对象建模
- 主流程为 `pending -> processing -> resolved -> closed`
- 可选分支保留 `pending -> rejected`
- tenant 负责 `create / close`
- landlord 负责 `process / resolve / reject`
- admin 复用同一套接口，可执行所有合法状态流

------

## 7. 报表统计模块

文档要求提供出租率、租金收入、用户活跃度等报表。

建议先做最实用的几个：

- 房源总数、已出租数、空置数
- 房源出租率
- 每月租金收入
- 用户数量增长
- 活跃用户数
- 维修申请数量统计
- 投诉数量统计

注意：
 第一版统计图不需要太复杂，有折线图、柱状图、饼图就够。

------

## 8. 系统监控与后台管理模块

文档提到管理员可查看运行日志和分析。

课程项目里建议做成：

- 登录日志
- 操作日志
- 异常日志
- 用户管理
- 房源管理
- 投诉处理
- 数据概览面板

真正的服务器监控、告警系统可以先不做重。

# 八、模块之间的关系

你后面画 ER 图时可以按这个理解：

- 一个房东可以有多个房源
- 一个房源可以有多个图片
- 一个房源可以被多个租客收藏
- 一个房源可以有多个预约
- 一个房源在某一时刻通常只对应一个有效合同
- 一个合同可以有多个租金账单
- 一个合同/房源可以有多个维修申请
- 一个租客可以提交多个投诉
- 一个房源相关咨询可以对应一个会话，会话下有多条消息

# 九、建议补充的需求

你原文档已经比较全，但如果你们要做得更像一个完整系统，我建议补几个非常实用的点。

## 1. 房源审核

管理员审核房源后才能上架。
 这样系统更合理，也方便管理员权限体现。

## 2. 收藏与浏览历史

租客通常需要反复比较房源，这个功能很实用。

## 3. 房源排序

比如：

- 最新发布
- 租金最低
- 面积最大
- 推荐优先

## 4. 消息通知

至少做站内通知：

- 预约确认通知
- 签约通知
- 支付提醒
- 报修处理通知

当前第一版补充约束：

- Notification 已落地为单用户站内通知模块
- 推荐 `source_type`：`repair / complaint / contract / bill`
- 当前自动触发来源：
  - Repair
  - Complaint
  - Contract
  - Bill / Payment
- 用户只能查看和标记自己的通知
- 第一版不做广播通知和批量已读

## 5. 房源下架规则

一旦签约成功，房源自动变“已出租”。

# 十、非功能需求怎么落地

文档里提到响应时间、并发、安全、可维护性、兼容性等。
 但课程项目里不能只写空话，要落到具体措施。

## 1. 响应时间

目标：常见操作 2 秒内响应。

落地方式：

- 列表分页
- 图片懒加载
- 常用查询加索引
- 减少重复请求

## 2. 并发处理

目标：支持 1000 用户请求。

课程项目里可以写成：

- 采用连接池
- 数据库关键字段建立索引
- 静态资源分离
- 使用缓存优化热点数据

## 3. 数据安全

文档提到传输加密、存储加密。

落地写法：

- 密码加密存储
- 敏感信息脱敏展示
- 登录验证码
- 权限校验
- 防止越权访问

## 4. 易用性

文档要求界面直观、1 天内学会。

落地写法：

- 表单校验与错误提示
- 统一按钮与导航风格
- 重要操作二次确认
- 空状态提示

# 十一、开发优先级建议

如果你们是课程设计，不要一上来全做，建议按 3 个阶段推进。

## 第一阶段：最小可运行版本

先做最核心闭环：

- 登录注册
- 角色区分
- 房源发布与展示
- 房源搜索
- 在线消息
- 预约看房

做到这里，系统已经能演示了。

## 第二阶段：租赁闭环

继续加：

- 合同管理
- 租金账单
- 支付记录
- 报修处理
- 投诉处理
- 房源状态联动

做到这里，就是完整业务系统。

## 第三阶段：增强功能

最后做：

- 新闻公告
- 报表统计
- 智能问答/推荐
- 日志管理
