# 后端项目结构说明（模块化单体 + 容器化依赖）

## 一、总体设计

本项目采用：

- 模块化单体架构（Modular Monolith）
- 分层设计（router / service / repository / model / schema）
- 容器统一注册（service / repository 单例）

核心目标：

- 提高内聚
- 降低耦合
- 支持多人协作
- 支持后续扩展或演进为微服务

请求链路：

router → service → repository → model

## 三、核心目录说明

### core（系统基础设施）

提供全局基础能力：

- config：配置管理
- database：数据库连接与 Session
- security：JWT 与认证
- exceptions：统一异常定义
- response：统一响应格式
- logging：日志配置

------

### common（公共抽象层）

提供跨模块复用能力：

- base_model：ORM 基类（id、时间字段、软删除）
- base_schema：统一序列化配置
- base_repository：基础 CRUD
- pagination：分页结构
- enums：统一状态枚举
- dependencies：权限依赖
- utils：工具函数

------

### container（依赖注入容器）

负责统一创建与管理实例（单例）：

- repositories.py：实例化所有 repository
- services.py：实例化所有 service（注入 repository）
- providers.py：对 router 提供依赖入口

职责：

- 统一初始化
- 控制依赖关系
- 提供注入接口

------

### modules（业务模块）

按业务划分，每个模块独立：

每个模块结构：

```text
module/
  model.py
  repository.py
  service.py
  schema.py
  router.py
```

职责：

- model：数据库表
- repository：数据访问
- service：业务逻辑
- schema：数据结构
- router：接口定义

## 五、分层职责

### router

- 接收请求
- 参数校验
- 调用 service
- 返回响应

### service

- 核心业务逻辑
- 权限控制
- 状态流转
- 多表协作

### repository

- 数据库操作
- 查询封装
- 不包含业务逻辑

### model

- 数据表定义

### schema

- 请求与响应结构
- 参数校验

## 六、容器设计

### repositories.py

```python
user_repository = UserRepository()
house_repository = HouseRepository()
```

------

### services.py

```python
user_service = UserService(user_repository)
house_service = HouseService(house_repository)
```

------

### providers.py

```python
def get_user_service():
    return user_service
```

------

### router 使用

```python
@router.post("/")
def create(data, service = Depends(get_user_service)):
    return service.create(data)
```

------

## 七、设计原则

1. 模块内聚

- 一个模块只负责一个业务域

1. 低耦合

- 模块之间尽量少依赖

1. 单向依赖

- router → service → repository → model

1. 公共能力下沉

- 放在 common 或 core

1. 容器统一管理实例

- 但代码仍按模块组织

1. 状态统一用枚举

- 避免字符串分散

------

## 八、约束

- 不集中所有 repository 到一个目录
- 不设计复杂 BaseService
- service 不保存请求状态
- db/session 通过参数传递
- 跨模块优先依赖 service，避免直接调用 repository

------

## 九、扩展与演进

该结构支持逐步演进：

### 阶段1

模块化单体（当前）

### 阶段2

模块内部细分（services/、repositories/ 等子目录）

### 阶段3

抽离公共基础设施（文件、消息、搜索）

### 阶段4

按模块拆分为独立服务（微服务）

说明：

- 不需要推翻结构
- 只需逐步演进

------

## 十、总结

该结构具备：

- 清晰的模块边界
- 明确的分层职责
- 统一的依赖管理
- 良好的扩展能力

适用于中小型系统，并可作为后续大型系统演进基础。
